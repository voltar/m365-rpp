# Architecture Decision (ADR-001)

The **Resources Presence Planner** will be developed as a central, multi-workspace enterprise application.

## Technology Stack

| Layer                     | Technology                         |
| ------------------------- | ---------------------------------- |
| Client                    | React (Vite + TypeScript)          |
| Host                      | Microsoft Teams Tab App            |
| API                       | ASP.NET Core Web API               |
| Database                  | Microsoft SQL Server Always On, or SharePoint Online lists — see [ADR-002](ADR-002.md) |
| Authentication            | Entra ID (OAuth/OIDC)              |
| Microsoft 365 Integration | Microsoft Graph                    |
| Documents                 | SharePoint Online                  |
| Persistence profile       | `sql` or `sharepoint`, per installation — see [ADR-002](ADR-002.md) |
| Deployment                | GitLab CI/CD → Kubernetes          |
| TLS / Ingress             | Existing Kubernetes infrastructure |

## Architectural Principles

### One application

* One code repository
* One API
* One frontend
* Many workspaces
* Many instances (can be deployed to different tenants, organizations)

Each workspace represents an organisational unit, a team, or a planning group.

Isolation is implemented logically through the data model, rather than through separate installations.

### Teams is the primary entry point

The application runs as a tab within Microsoft Teams.

The same URL can also be used directly in a browser in the future, if required.

### SQL is the source of truth

> **Superseded by [ADR-002](ADR-002.md) (2026-07-31).** This section held while SQL Server was the
> only store. The application now supports two persistence profiles — `sql` and `sharepoint` —
> selected per installation as deployment configuration. The text below is kept as the record of
> what was decided originally; read ADR-002 for what applies. The rest of ADR-001 is unaffected.

All business data is stored in SQL Server.

SharePoint is used only for documents and file attachments.

### Business logic belongs in the backend

The client should remain as lightweight as possible.

Rules, validations, and authorisation checks are centrally implemented in the API.

## Why This Is a Strong Long-Term Foundation

I can already see several potential future expansion areas:

* Approval workflows
* Capacity planning
* Resource reservations
* Dashboards
* Historical reporting
* Forecasting
* Exports
* Integrations with SAP or HR systems
* Mobile clients
* Public REST API

With a central API and SQL Server as the foundation, these capabilities can be added without changing the underlying architecture.
