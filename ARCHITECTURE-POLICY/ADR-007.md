# Architecture Decision (ADR-007)

**The relational planning profile supports two database engines: SQL Server and PostgreSQL.**

Status: Accepted 2026-08-08 (implemented with EO-458)  
Extends: [ADR-002](ADR-002.md) (persistence profiles `sql` / `sharepoint`)  
Does not change: SharePoint profile, mock registration, or the rule that the browser never talks to a database  
Implementation: [EO-458](../ENGINEERING-ORDERS/EO-458.md)

## Context

ADR-002 defines two **persistence profiles**:

| Profile | Store |
|---------|--------|
| relational (configured today as `sql`) | Database via EF Core |
| `sharepoint` | SharePoint Online lists |

The relational profile was implemented only with **Microsoft SQL Server / Azure SQL**. That fits Azure App Service and many enterprise estates. It is a poor default for:

* Linux VPS / Host Europe / generic Kubernetes without a SQL Server license,
* local and CI stacks that already run PostgreSQL,
* customers who standardise on PostgreSQL as the only RDBMS.

EF Core already abstracts the repository (`EfPlanningRepository` + `RppDbContext`). The missing piece is **engine selection at startup**, not a second data model.

## Decision

1. The **relational** persistence profile may run on either:
   - **SQL Server** (including Azure SQL) — configuration value `sql` (unchanged default in shipped `appsettings.json`), or
   - **PostgreSQL** — configuration value `postgres` (aliases `postgresql`, `npgsql` accepted).

2. Selection remains **deployment configuration** via `Planning:Provider`, resolved at startup with **no silent default in code** when the value is missing or unknown (same failure class as EO-430 / ADR-002).

3. Both engines share:
   - `RppDbContext` and entity configurations,
   - `EfPlanningRepository` / `IPlanningRepository`,
   - the same API surface; the frontend stays unaware.

4. Connection strings stay in `ConnectionStrings:DefaultConnection` (or the platform secret store). Format is engine-specific (SQL Server vs Npgsql).

5. **Schema evolution:**
   - **SQL Server:** existing EF Core migrations under `Migrations/` continue to apply via `Database.Migrate()` at startup.
   - **PostgreSQL (v1):** schema is created from the current model when the database has no tables (`IRelationalDatabaseCreator.CreateTables`). Full dual migration assemblies are a deliberate follow-up if PostgreSQL installations need in-place upgrades without recreate; until then, model changes on PostgreSQL are operator-managed (migrate tooling or recreate empty DB in non-prod).

6. Health / diagnostics report the engine (`PlanningStore` name and `BackendProvider` string) so support can see SQL Server vs PostgreSQL without reading App Settings blindly.

## Consequences

* ADR-002’s table gains an engine dimension under the relational profile; the SharePoint profile is unchanged.
* Host Europe and similar Linux hosts can run the full API with PostgreSQL without SQL Server.
* Azure installations keep `Planning:Provider=sql` and behaviour is unchanged.
* Filtered indexes and other provider-specific DDL are applied in a **provider-aware** model configuration (not hardcoded T-SQL only).
* Adding a third engine later follows the same pattern; it is not implied by this decision.

## Not decided here

* Managed PostgreSQL vendor (Azure Database for PostgreSQL, on-box Docker, Host Europe managed DB, etc.).
* Automated dual-provider migration pipelines in CI.
* Changing the SharePoint profile or introducing a server-free browser→SharePoint product.
