# Architecture Decision (ADR-002)

**Two persistence profiles, selected per installation.**

Status: Accepted 2026-07-31
Supersedes: the *"SQL is the source of truth"* section of [ADR-001](ADR-001.md). Everything else in
ADR-001 stands unchanged.
Driven by: EO-430

## Context

ADR-001 states:

> **SQL is the source of truth.** All business data is stored in SQL Server. SharePoint is used only
> for documents and file attachments.

That was correct for the installation ADR-001 was written for: a customer with Kubernetes, a CI/CD
pipeline and a SQL Server Always On cluster already running. It is wrong for a customer who is not
going to run a **database** for a planning application — backups, patching and availability are a
standing operational burden per installation, and a planning tool rarely justifies one.

There is a second reason, and it is the one that decides the matter rather than cost. In the
SharePoint profile the lists are not merely a store — they are a **second editing surface**.
Administrators and HR maintain data directly in them: choosing a person through the People Picker,
entering absences in a calendar view, importing holidays. No relational database offers that at any
price, because it has no user interface. Where that capability is wanted, SharePoint is not the
cheaper substitute for SQL Server; it is a different thing that happens to also store data.

## Decision

The application supports **two persistence profiles**. Which one an installation runs is
**deployment configuration**, resolved at startup, not a build-time or code-level choice.

| Profile | Store | Serves |
|---------|-------|--------|
| Relational (`sql` or `postgres`) | SQL Server / Azure SQL, or PostgreSQL via EF Core — see [ADR-007](ADR-007.md) | The scaling tier: larger installations, existing database operations, unbounded history |
| `sharepoint` | SharePoint Online lists in the customer's tenant | The entry tier: installations without a database, and installations that want the lists as an editing surface |

Configuration still uses `Planning:Provider`. Values `sql` and `postgres` both select the relational
profile with different engines (ADR-007). `sql` remains the shipped default for Azure SQL estates.

Both profiles serve the same `IPlanningRepository` contract behind the same API. The frontend is
unaware of the choice — it talks to the API in both cases (ADR-003), and no client ever reaches a
store directly.

`mock` remains available as a third registration for demonstration and development. It is not a
persistence profile and is not deployed to a customer.

## What the entry tier does not remove: the host

Both profiles need a web host, and the entry tier does not change that. Two independent reasons:

* **The frontend has to be served from somewhere.** A Microsoft Teams tab is a webview pointing at
  an HTTPS URL. The app package carries the manifest and icons; Teams hosts no application files.
  The React bundle *executes* in the Teams client, but it is *delivered* by a web server — today the
  API itself, which serves the built SPA from `wwwroot` with a fallback to `index.html`
  (`Program.cs`). There is no separate frontend server, and no server-side rendering.
* **Several features need application permissions.** Inbound mailbox sync, the help assistant,
  Outlook calendar sync, the profile photo proxy, Graph membership reads and the approval callback
  endpoint all run app-only or need a reachable endpoint. App-only means a client credential, which
  cannot live in a browser, and a background sync has to run when no one is looking.

The saving in the entry tier is therefore the **database**, not the host. Hosting the API alongside
the static files it already has to serve costs little beyond serving them.

A genuinely server-free variant — the browser talking to SharePoint directly, delegated — is
technically possible and partly prepared for in the client code, but it is a **different product**:
it drops the six capabilities above. If that is ever wanted it belongs in its own decision, with the
reduced scope stated up front, not as an implicit reading of this one.

## What each profile guarantees

This is the part ADR-001 never had to state, because with one store the guarantees were simply
properties of the platform. With two, they differ, and the difference is the decision's real
content.

| | `sql` | `sharepoint` |
|---|---|---|
| Transactions | Yes, per `SaveChanges` | **None.** Multi-entity writes are ordered and compensated by the application |
| Joins across entities | Yes | **None.** Reads are per list; correlation happens in the application |
| Referential integrity | Enforced by the database | Enforced by the application, or not at all |
| Compound unique keys | Enforced by the database | Enforced by the application; SharePoint enforces single-column uniqueness only |
| Query volume | Bounded by hardware | Bounded by the 5000-item list view threshold and by tenant throttling |
| Schema evolution | EF Core migrations | The provisioning script, validated at startup |
| Second writer | The application only | The application **and people**, editing the lists directly |

Guarantees the SQL profile provides for free become **application obligations** in the SharePoint
profile. They are not thereby made optional.

## Bounded, and stated

The SharePoint profile is deliberately limited. The 5000-item list view threshold, the throttling
budget and the absent transactions are not engineered away; they are bounded and published, with a
supported installation size beyond which the answer is the SQL profile. An installation that
outgrows the entry tier is a success, and migrating it is a planned step rather than an incident.

A profile that reports its limits is sound. Neither profile may fail silently — a lost write, a
dropped row or a stale number is a defect in both, and being the cheaper profile excuses none of it.

## Consequences

* One code base, one API and one frontend continue to serve every installation. ADR-001's *One
  application* principle is unaffected — this decision adds a store, not a variant.
* `EfPlanningRepository` is not removed. Both implementations are maintained, and every future
  change to the persistence contract costs two implementations rather than one. The SharePoint
  implementation cannot be verified without a tenant, which is the larger part of that cost.
* Business logic stays in the backend, per ADR-001. Authorization in particular remains in the
  controllers for both profiles; no store-level permission model substitutes for it.
* SharePoint's role in ADR-001's technology stack changes from *Documents* to *Documents and
  entry-tier planning data*. The table there is updated accordingly.
* Calculated values remain calculated in both profiles. Nothing about this decision makes a stored
  vacation balance or capacity figure acceptable.

## Not decided here

* Who may edit the SharePoint lists directly. SharePoint permissions have no notion of the
  application's team boundaries, and answering this casually would create a second permission model
  beside the tenant's. Open in EO-430.
* Migration of an existing installation's data between profiles. Both directions are out of scope
  until there is an installation that needs it.
* A server-free variant. See *What the entry tier does not remove* — it would need its own decision
  and its own reduced scope, and is not implied by this one.
