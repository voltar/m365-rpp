# Architecture Decision (ADR-004)

**One application, multiple hosts — host concerns behind a single adapter, one build artefact.**

Status: Accepted 2026-08-07 (implemented via EO-455)
Extends: [ADR-001](ADR-001.md) (*Teams is the primary entry point*, *One application*)
Orthogonal to: [ADR-002](ADR-002.md) (persistence profiles) and the runtime **data** provider
selection described as ADR-003 in architecture docs (`mock` | `sharepoint` | `api` on the client;
server `Planning:Provider` for the store)
Driven by: product need for deep links and additional surfaces (browser, SharePoint Web Part)
without a second product or second frontend build
Implementation vehicle: [EO-455](../ENGINEERING-ORDERS/EO-455.md)

## Context

ADR-001 states:

> **Teams is the primary entry point.** The application runs as a tab within Microsoft Teams. The
> same URL can also be used directly in a browser in the future, if required.

That future is now concrete. Deep links already open the app on a specific planning object
(EO-421 / EO-421R: Outlook-synced events carry a Teams entity link with `subEntityId`). The same
product surface is expected to appear:

* as a **Microsoft Teams** tab (channel and personal scope) — primary host today,
* as a **standalone browser** session (same deployed URL, no Teams chrome),
* as a **SharePoint** surface (full page and/or Web Part), without forking the application.

Today the host boundary is implicit. `AppShell` always calls `initializeTeamsApp()`, theme and
deep-link code race the Teams SDK with timeouts, `resolveCurrentUserId` / `resolveActiveTeamId`
construct a `TeamsSsoAuthProvider` even outside Teams, and demo chrome is gated on
`planningDataSource === "mock"` rather than on the actual host. That works for the Teams-first
path and for a tolerant browser demo; it does not scale cleanly to SharePoint, and it pays avoidable
cost (SDK work and multi-second timeouts) on every non-Teams session.

A second Vite/SPFx build of the same UI would violate ADR-001's *One application* principle in
practice: two artefacts drift, two auth stacks, two release labels, and no single
`npm run package:api` path.

## Decision

The application supports **multiple hosts** behind one **Host Adapter** contract. Which host a
session runs in is resolved **once at startup**, not at build time, and not per HTTP request.

| Host | Typical surface | Auth | Team scope |
|------|-----------------|------|------------|
| `teams` | Teams tab (channel or personal) | Teams SSO (`TeamsSsoAuthProvider`) | Channel: host `groupId`. Personal: user selection only (EO-428) |
| `browser` | Direct HTTPS URL | MSAL (or mock when data source is mock) | User selection only (EO-428) |
| `sharepoint` | SharePoint page or Web Part mount | SPFx / page-context token bridge implementing the same `Microsoft365AuthProvider` | User selection, or an **explicit** Web Part property — never inferred from the SharePoint site |

There is **one frontend build artefact**. SharePoint integration is a mount or iframe onto that
artefact (plus a thin host bootstrap that sets host kind and context). It is not a second React
application and not a second `dist`.

### Host is not data

Two independent axes must not be conflated:

| Axis | Configured by | Values | Owns |
|------|---------------|--------|------|
| **Data / persistence** | Runtime / deployment config (ADR-002, ADR-003) | `mock` \| client `sharepoint` \| `api`; server `sql` \| `sharepoint` | Where planning facts live and how repositories are composed |
| **Host** | Session detection or embedder bootstrap (this ADR) | `teams` \| `browser` \| `sharepoint` | Auth handshakes, theme, chrome, deep-link wire format, ready notification |

A Teams tab can run against the API or against mock data. A SharePoint-hosted session can talk to
the same API. Choosing SharePoint as a **host** does not select SharePoint as a **planning store**,
and EO-430 remains a separate decision about persistence.

### Adapter contract (normative shape)

All host-specific behaviour is reached only through a session-scoped adapter. UI features,
repositories and services do not import `@microsoft/teams-js` or SPFx types directly.

The adapter exposes at least:

* **Identity of the host** — `kind`: `teams` | `browser` | `sharepoint`
* **Lifecycle** — idempotent `initialize()`, `notifyReady()` (Teams loading indicator; no-op elsewhere)
* **Context** — user id, tenant, locale, optional team id/name; **memoized for the session**,
  invalidated only on host-signalled changes
* **Auth** — `getAuthProvider(): Microsoft365AuthProvider` (existing contract in
  `authContracts.ts`)
* **Theme** — observe host theme; browser falls back to `prefers-color-scheme`
* **Chrome** — which shell chrome to show (app header, demo Teams rail, workspace nav, full-page
  vs embedded)
* **Deep link** — `readDeepLink()` / `buildDeepLink()` over a **host-neutral target language**

Canonical deep-link targets (examples; extensible without new hosts):

* `vacation-request:{id}` — timeline + details (EO-421R behaviour)
* `absence:{id}`
* `route:{path}` — workspace hash route
* `help:{topic}` — help drawer, not a route

Wire formats differ by host; the target language does not:

| Host | Inbound example | Outbound example |
|------|-----------------|------------------|
| Teams | `subEntityId` / `subPageId` | `https://teams.microsoft.com/l/entity/{appId}/{entityId}?context=…` |
| Browser | `location.hash` + query | Absolute app URL + hash/query |
| SharePoint | Hash of the mounted SPA, iframe URL, or explicit Web Part property | Site page URL + hash, or a Teams entity link when mail/calendar should open the primary host |

### Detection order

Host resolution runs once and is memoized:

1. **Explicit bootstrap** — embedder sets e.g. `window.__RPP_HOST__` (and optional host context)
   before mount. Required for in-page SharePoint mounts.
2. **Teams** — reliable in-Teams detection (SDK / known host frame signals), without treating
   “SDK might hang” as the detection strategy.
3. **SharePoint** — page or SPFx context present at mount.
4. **Browser** — default.

The Teams SDK and any SharePoint bridge are loaded **only for the resolved host** (dynamic
`import()`). Non-Teams sessions must not pay Teams initialize/getContext timeouts.

### Chrome and surface width

* Inside the real Teams client, in-app duplicates of host chrome stay off (today’s intent;
  demo rail/header remain mock/browser affordances).
* A full-page SharePoint page may show the normal workspace navigation.
* A narrow Web Part may restrict chrome and optionally the set of routes it preloads; that is a
  **capability** of the adapter, not a separate application.
* Route-level code splitting stays as it is; the adapter does not eagerly pull every feature.

### Team context rule (unchanged, restated)

EO-428 remains binding on every host:

> Team identity comes from an explicit host team scope or from the user’s own stored choice.
> There is no silent fallback team.

Personal Teams scope, browser, and SharePoint default to the picker / stored selection path.
Substituting a team the user did not choose is a defect on every host.

## Consequences

* ADR-001’s *One application* and *one frontend* remain literal: one repository, one API, one
  `dist`, one release label (`release.json` / EO-427 packaging path).
* Teams remains the **primary** entry point and the preferred deep-link target for mail and
  calendar (“open in RPP”), even when a SharePoint surface exists.
* `TeamsContext` / ad-hoc Teams calls in shell, deep-link and current-user helpers move behind the
  adapter; `Microsoft365AuthProvider` stays the auth boundary.
* Session-cached host context removes the known anti-pattern of resolving Teams context on every
  API request (performance analysis), without changing repository contracts.
* SharePoint-as-host work is packaging and adapter implementation, not a product fork. It does
  **not** implement or unlock EO-430 write paths.
* Backend deep-link generation (e.g. Outlook sync) may keep emitting Teams entity URLs; the client
  adapter is responsible for inbound resolution on whichever host actually opened the app.

## Not decided here

* ~~Whether SharePoint hosting is delivered as iframe or in-page mount.~~ **Decided for future
  work in [ADR-006](ADR-006.md): v1 is iframe embed of the deployed SPA (EO-457). In-page SPFx
  mount remains a possible later upgrade.**
* Which Web Part sizes or route allow-lists ship first. Capabilities are in the contract; the
  product cut is an EO/scope choice (see EO-457).
* Changing ADR-002 persistence profiles or client runtime data providers.
* A fully server-free, browser-only SharePoint-delegated product (explicitly out of ADR-002 as
  well).
* Replacing hash routing or introducing React Router.

## Relationship to existing code (orientation, not mandate)

The following are the natural seams when the decision is implemented; naming may differ:

* New: `src/infrastructure/host/` (resolver + adapters)
* Existing contracts to preserve: `Microsoft365AuthProvider`, runtime-config data axis,
  `createDefaultPlanningRepositories`, hash routes in `AppShell`
* Existing call sites to re-home: `initializeTeamsApp` / `observeHostTheme`,
  `resolveDeepLinkVacationRequestId`, `resolveCurrentUserId` / `resolveActiveTeamId` /
  `resolveActiveTeamName`, demo chrome gating in `AppShell`
* Existing stub: `src/webparts/resourcePresencePlanner/ResourcePresencePlannerWebPart.tsx` becomes
  a mount over the same shell, not a second app

## Acceptance of this decision

Accepted with EO-455 implementation (2026-08-07). The paired engineering order is EO-455.
