# Architecture Decision (ADR-006)

**SharePoint surface v1 is an iframe embed of the existing SPA URL — not an in-page SPFx React mount.**

Status: **Decided for future work** 2026-08-08 (not implemented; not scheduled)  
Extends: [ADR-004](ADR-004.md) (host adapter; one build artefact)  
Orthogonal to: [ADR-002](ADR-002.md) (persistence profiles) — SharePoint-as-**host** ≠ SharePoint-as-**store**  
Implementation vehicle (when pulled): [EO-457](../ENGINEERING-ORDERS/EO-457.md)

## Context

ADR-004 left open how SharePoint hosting is delivered:

> iframe to the existing URL **or** in-page mount with a token bridge.

After EO-455 the runtime host `sharepoint` and a thin React mount stub exist, but nothing is
packageable in a tenant App Catalog. Two delivery shapes remain possible:

| Route | Shape |
|-------|--------|
| **A – iframe** | A minimal SPFx (or Embed) Web Part loads the **already deployed** RPP HTTPS origin (`contentUrl` / `api` host) in an iframe. One SPA artefact; Web Part is a shell. |
| **B – in-page mount** | SPFx loads the bundle into the page DOM and supplies `__RPP_HOST__` + an `AadTokenProvider` bridge implementing `Microsoft365AuthProvider`. |

## Decision

**v1 uses Route A (iframe).**

Product and engineering reasons:

1. **One artefact stays literal** — no second React graph, no SPFx-duplicated Fluent tree, no drift from `npm run package:api`.
2. **Auth stays on the known host** — Teams/Azure (or Host Europe) Application ID URI and SSO path already work for that origin; Entra does not need a `*.devtunnels.ms`-style experiment for SharePoint.
3. **Faster path to “visible in SharePoint”** — SPFx work is packaging, properties, catalog, and frame permissions, not a second client runtime.
4. **EO-430 is untouched** — lists as planning store remain a separate decision.

Route B remains a **possible later upgrade** if iframe limits (third-party cookies, chrome, deep linking, mobile) prove unacceptable. It does not invalidate this ADR; it would be a new decision or an amendment with explicit scope.

## Consequences (when EO-457 is built)

* SPFx solution is a **thin host**: Web Part properties (at least target URL and optional `teamId` / deep-link query), iframe, loading/error chrome.
* Deployed RPP origin must allow being framed by the tenant’s SharePoint hosts (`Content-Security-Policy: frame-ancestors` or equivalent) without weakening the general security baseline.
* `runtime-config` on that origin stays `planningDataSource: api` (or mock for demo); the Web Part does not select ADR-002 store profiles.
* Team scope follows EO-428: explicit Web Part property and/or in-app picker — **never** inferred from the SharePoint site URL alone.
* Host detection inside the iframe may resolve as `browser` or `teams` depending on outer frame signals; that is acceptable for v1 if auth and team context work. Optional: query/`__RPP_HOST__=sharepoint` only if the outer shell sets it before navigation (iframe document is still the SPA origin).
* Backend-generated deep links may keep preferring Teams entity URLs; SharePoint is an additional surface, not the primary mail/calendar target.

## Not in this decision

* Building or scheduling EO-457.
* In-page SPFx token bridge (Route B).
* SharePoint Online as planning persistence (EO-430).
* Replacing Teams as the primary entry point (ADR-001).

## Record

Product Owner direction 2026-08-08: pursue Route A when SharePoint Web Part work is scheduled.
