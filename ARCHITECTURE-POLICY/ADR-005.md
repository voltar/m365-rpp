# Architecture Decision (ADR-005)

**First use of RPP in an M365 team seeds a default planning cohort — never an empty people list.**

Status: Accepted 2026-08-07 (implemented via EO-456)
Extends: [ADR-001](ADR-001.md) (*One application*, operational visibility)
Builds on: EO-418 / EO-419 (M365 host team vs internal RPP teams via `OwningTeamId`), EO-420
(owners reach Team Admin without structures; membership gate uses Graph), EO-428 (no silent
fallback **host** team)
Driven by: empty Timeline / “no plannable people” when the app is first added to an M365 team
Implementation vehicle: [EO-456](../ENGINEERING-ORDERS/EO-456.md)

## Context

RPP distinguishes two team concepts:

| Concept | Identity | Role |
|---------|----------|------|
| **M365 host team** | Teams / Entra group id (`OwningTeamId`, `X-RPP-Active-TeamId`) | Who may open the app instance; Graph membership and ownership |
| **Internal RPP planning team** | `TeamAdminTeam.TeamId` | How people are grouped on the Timeline, capacity, assignments |

Planning memberships served to the Timeline are built from **assignments** to internal teams, not
from the raw Graph member list alone (`GetTeamMembershipsAsync`). Graph supplies who *exists* in
the host; assignments supply who is *plannable* and in which RPP team.

EO-420 correctly stopped locking owners out when no internal structures exist, and gates access on
real M365 membership. It did **not** create structures. The first session after adding the app to a
team therefore often shows a healthy shell and **zero people** — “Keine planbaren Personen” —
until a team owner manually creates RPP teams and assigns every member. That is technically
consistent and product-wrong: the M365 team already has a known member set (members and guests).
Operational visibility on day one should not require a blank-slate configuration ritual.

EO-428 forbids substituting a **host** team the user did not choose. That rule is about *which
M365 team the request is scoped to*. It does not forbid creating a default **internal** planning
team *inside* a host scope the user (or the tab) already resolved.

## Decision

When RPP is used in an M365 host team that has **no internal planning teams** for that
`OwningTeamId`, the application **seeds exactly one default internal team** and assigns **every
current Graph member of that host** (members and guests) to it as **primary** assignment.

### Naming

Default display name:

```text
Alle - {M365 team display name}
```

Examples: `Alle - IT Platform Services`, `Alle - Projekt Rollout X`.

* `{M365 team display name}` is the Microsoft 365 group/team **display name** from Graph (already
  available via existing team display-name resolution), not a SharePoint URL and not a hardcoded
  organisation string.
* The `Alle - ` prefix is a fixed product pattern (localised display may follow in the EO; the
  stored default name uses this pattern unless localisation of *stored* names is explicitly
  required).
* The name is a normal team name: owners may rename or restructure later in Team Admin. Seeding
  does not freeze the structure.

### When

Seeding is **lazy and idempotent**, tied to the host scope:

* **Trigger:** first server-side planning read (or Team Admin read) that is scoped to a concrete
  M365 host team id and finds **zero** `TeamAdminTeam` rows with that `OwningTeamId`.
* **Not** on app package install alone (Teams does not reliably give the API a webhook for “tab
  added”), and **not** from a global default host id in configuration (EO-428).
* **Not** when the host already has one or more internal teams — including the case where an owner
  deleted everyone from the default team or replaced it. Absence of people after deliberate admin
  work must not be “fixed” by silent re-seed.
* Concurrent first requests for the same host must not create duplicate default teams (unique
  constraint and/or transactional check per `OwningTeamId`).

### Who is assigned

* All principals returned by the existing Graph membership fetch for that host team, including
  **guests**, matching who EO-428 treats as part of the M365 team.
* Each person gets a **primary** assignment to the default internal team.
* No secondary positions are invented.
* Approver / team-lead fields stay empty unless a later rule says otherwise; owners configure
  policy in Team Admin as today.
* If Graph is unavailable at seed time, seeding **fails closed for the create path**: do not write
  an empty default team that would block a later successful seed; surface a recoverable error or
  retry on the next request when Graph succeeds. (Exact UX is EO scope.)

### What seeding is not

* It is **not** a second membership source. After seed, Timeline still reads assignments;
  Graph remains the directory of host membership for Team Admin “assignable people” and access
  gates.
* It is **not** continuous sync of M365 membership into the default team. People who **join the
  M365 team later** are visible as assignable in Team Admin; auto-adding them to the default
  cohort is a separate product choice (see *Not decided*). Day-one seed only guarantees the
  initial cohort.
* It is **not** creation of a fallback **host** team when `X-RPP-Active-TeamId` is missing.
* It does **not** seed demo absences or balances in production (development seeders stay behind
  their existing flags).

### Relationship to manual Team Admin

After seed, the default team is ordinary data:

* Rename, split into multiple RPP teams, change primary assignments, set approvers — all as today.
* Deleting the last internal team for a host returns the host to the “no structures” state; the
  next scoped read may seed again **only if** the product rule remains “zero internal teams ⇒
  seed”. That re-seed-after-delete behaviour is accepted as the cost of the simple rule; owners
  who want an empty planning surface must keep at least one internal team and clear assignments
  (or a future EO may add an explicit “do not auto-seed” flag — not part of this decision).

## Consequences

* First open of RPP on a newly connected M365 team shows **people immediately** under
  `Alle - {team name}`, which matches user expectation and ADR-001 operational visibility.
* EO-420’s empty Team Admin “create first team” path becomes the exception (Graph failure, or
  races), not the happy path.
* User documentation that says “no members are assigned yet” after a fresh install must be updated
  when EO-456 ships.
* Server-side responsibility: seeding lives in the API/repository layer for the **api** (and later
  SharePoint store) profile — not in the React bundle inventing teams.
* Mock/demo mode may mirror the same named default cohort for realism; it must not write to
  customer stores.

## Not decided here

* Whether **later** M365 joiners are auto-assigned to the default internal team (membership delta
  sync). Default for EO-456: **initial seed only**.
* Whether renaming the M365 team renames `Alle - …` automatically. Default: **no** — name is a
  snapshot at seed time; owners rename in Team Admin if needed.
* Per-installation opt-out of auto-seed.
* Required staffing, approval policy, or colours on the default team beyond safe empty/optional
  defaults already used by `CreateTeamAsync`.
* Client-only / SharePoint-list profile behaviour beyond “same rule when that store implements
  team admin writes”.

## Acceptance of this decision

Accepted with EO-456 implementation (2026-08-07). The paired engineering order is EO-456.
