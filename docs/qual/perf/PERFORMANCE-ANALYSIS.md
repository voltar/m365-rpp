# Performance analysis — M365 RPP Teams App

Read-only analysis. No application code was changed; the only files added are the two in `perf/`.

## What was measured vs. estimated

| # | Method | Result |
|---|---|---|
| M1 | `npx vite build` on this checkout | 14.1 s, 2 500 modules, 76 emitted chunks |
| M2 | Parsed `dist/index.html` `modulepreload` list + `stat`/`gzip -c` per file | Initial JS **2 458 KB raw / 723 KB gzip across 47 files**; 39 locale chunks = **1 619 KB raw / 488 KB gzip = 67 % of it** |
| M3 | Chromium 1194 (Playwright 1.56.1) against `vite preview` of the production build, mock provider, viewport 1440×900 | 53 JS requests, 786 261 B transferred, 2 610 680 B decoded; **34 790 DOM nodes, 32 145 `<button>` elements**; JS heap 31 MB |
| M4 | Same, CDP `Network.emulateNetworkConditions` at 400 ms RTT / 1.6 Mbit down ("Teams mobile on a bad connection") | DOMContentLoaded **5 473 ms**, FCP **5 560 ms**, painted timeline **13 854 ms** |
| M5 | Same, unthrottled localhost | DOMContentLoaded 248 ms, FCP 320 ms, painted timeline 7 945 ms |
| M6 | `npx tsc --noEmit` / `npx eslint "src/**/*.{ts,tsx}"` | 9.0 s / 8.1 s — build gates are not a bottleneck |
| — | Everything else | Static analysis. `dotnet` is not installed in this environment, so **no backend timing, SQL plan, or endpoint payload was measured**. Backend findings are read from source and are marked as such. |

M3–M5 ran in **mock mode** (`planningDataSource: "mock"`, 31 seeded people, 16 seeded absences). With the `api` provider the DOM numbers are driven by real team size and the network numbers get the API round trips added on top — the browser-side costs below are therefore a **floor**, not a ceiling.

### Areas checked and found healthy

- **React memoization.** `Timeline.tsx` wraps essentially every derived value in `useMemo` and every handler in `useCallback`; `TimelineGrid`, `TimelineRow`, and `EventLayer` are all `memo`-wrapped with stable props. The render cost is DOM volume, not re-render churn.
- **Route code splitting.** All eight routes plus the help drawer are `React.lazy`, with hover/focus preloading (`PlaceholderPage.tsx:29-90`, `AppShell.tsx:38-43`). Route chunks are 5–47 KB.
- **Event-listener hygiene.** Every `addEventListener`, `ResizeObserver`, and `hashchange` subscription found has a matching cleanup (`SidePanel.tsx:45-46`, `PersonProfileCard.tsx:38-39`, `TimelineViewport.tsx:32-35`, `AppShell.tsx:124,140`). No leaked intervals — there are no `setInterval` calls in `src/`.
- **SharePoint provider query shaping.** `sharePointPlanningRepositories.ts` uses `$select`, `$filter`, and `$top` on every list and follows `@odata.nextLink` — noticeably better discipline than the API provider.
- **Token caching.** `CachedMicrosoft365AuthProvider` caches per scope set with a 60 s expiry skew (`cachedAuthProvider.ts:12-51`); tokens are not re-acquired per render.
- **Static asset caching.** Hashed `/assets` get `public,max-age=31536000,immutable`; `index.html` and the runtime config get `no-cache` — correct, and it fixed a real stale-bundle incident (EO-420).
- **Bot / message extension.** None. `teams-app-package/manifest.json` declares `staticTabs` only, so the activity-acknowledgement and adaptive-card questions do not apply.
- **Build gates.** `tsc --noEmit` 9.0 s, `eslint` 8.1 s, `vite build` 14.1 s. Nothing to fix.

## (a) Best benefit-to-effort ratio

1. **Lazy-load the locale bundles** — `src/localization/translations.ts`. Roughly half a day of work removes **488 KB gzip (67 % of initial JS) and 38 HTTP requests** from every single tab open, on every route, for every user. Measured, not estimated. Nothing else in this report is close on that ratio.

2. **Reduce the timeline's fixed 12-month lookback** — `Timeline.tsx:696`. Changing one constant to a period-relative window cuts the default view from 456 to ~120 day-columns — a ~74 % cut in the 32 145 DOM nodes measured. Full virtualization is the better long-term answer, but this is one line for most of the benefit, and it is worth confirming with the product owner that a year of history is genuinely wanted in the default view.

3. **Cache the Teams context + drop the two `/info`-only probes** — `currentUser.ts:47`, `PlaceholderPage.tsx:148-176`. Half a day removes ~11 host `postMessage` round trips and 2 uncacheable network requests from the pre-first-paint path. These matter most exactly where the app is slowest: high-latency mobile, where M4 measured 5.6 s to first contentful paint.

Runner-up, if backend work is in scope this sprint: **`AsNoTracking()` + push the team-admin `Where` clauses into the `IQueryable`** (`EfPlanningRepository.cs`). Mechanical, low-risk, and it is the difference between queries that scale with a team and queries that scale with the tenant.

## (b) Load test

`perf/rpp-load-test.js` — ready to run, no code changes required.

```bash
k6 run perf/rpp-load-test.js \
  -e BASE_URL=https://<host> \
  -e TOKEN=$(az account get-access-token --resource api://<client-id> --query accessToken -o tsv) \
  -e TEAM_ID=<m365-group-id>
```

**Sizing.** Assumes an organisation of ~1 200 licensed users, ~35 % opening the tab on a given workday, with the peak concentrated in the 08:00–09:00 window → **120 concurrent sessions at peak**. Override with `-e VUS_PEAK=…` / `-e VUS_SOAK=…`.

**Scenarios**

| Scenario | Shape | Critical path exercised | Why it is in the test |
|---|---|---|---|
| `morning_rush` | ramping-vus 0 → 30 → 120 over 5 min, hold 5 min, ramp down 2 min | `GET /` + every asset `index.html` preloads, then the full bootstrap | The one that surfaces the 2.5 MB payload and the uncached Graph calls behind `/access` and `/memberships`. Asserts `Cache-Control: immutable` survived deployment. |
| `working_day` | constant 30 VUs, 12 min, starting at t+1 min | The 9 parallel bootstrap calls (`memberships`, `absences`, `vacationbalances`, `holidays`, `settings`, `events`, `teamconfigurations`, `access`, `health`) | Steady-state re-bootstrap; records the `/absences` payload size so the full-table finding shows up as a number that grows over time. |
| `absence_writes` | constant-arrival-rate, 6/min, 10 min | `POST /api/planning/absences` → `CanWriteForUserAsync` → Graph owner check → `DELETE` cleanup | The only write path with a Graph call inside the authorization check. Cleans up after itself so repeat runs do not inflate the very table the read path returns in full. |
| `team_admin` | constant-arrival-rate, 10/min, 10 min | `teamadmin/teams`, `teamadmin/details/__all-teams`, `displayconfig`, `my-teams` | The full-table-scan endpoints, plus the uncached `my-teams` Graph lookup. |

**Thresholds** (starting budgets — tighten once a baseline exists): bootstrap p95 < 2 500 ms / p99 < 5 000 ms; `/health` p95 < 200 ms; `/absences` p95 < 800 ms; `/memberships` p95 < 1 200 ms; `teamadmin/details` p95 < 1 500 ms; HTTP failure rate < 1 %; auth failure rate < 1 %. The cold-load byte threshold is set to **p95 < 900 KB** — with the locale fix and compression in place that passes comfortably; today it should fail, which is the point.

The script writes `perf/rpp-load-test-report.html` and prints a JSON summary of the five headline numbers to stdout.

### Caveats

- Run it against a **non-production** deployment. `absence_writes` creates and deletes real rows; without `-e EMPLOYEE_ID` it degrades to exercising the authorization path only.
- A single static `TOKEN` means every VU is the same identity, so server-side per-user caches will look warmer than reality. For a truer picture, supply a token pool.
- **Graph throttling is a shared-tenant resource.** A 120-VU run against a live tenant can trip Graph limits for other applications, and with no `Retry-After` handling (see the throttling finding) the app has no graceful path out. Coordinate with whoever owns the tenant before the first peak run.
